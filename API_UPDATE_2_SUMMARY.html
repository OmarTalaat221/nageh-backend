Najeh API Documentation

ملخص تحديثات الـ API

Update-2 — كل ما هو جديد بعد الـ baseline المعروف بـ Update-1
هذا المستند مُعدّ لمطوّر تطبيق الموبايل. يغطي كل إندبوينت تأثّر بالتحديث، مقسّمًا حسب الدور (طالب / معلم / أدمن)، مع أمثلة Request & Response وجدول مرجعي سريع في النهاية.

التفاصيل التقنية الخام (JSON Schema الكامل) موجودة في ملف najeh_api_openapi.json المرفق.

هذا السماري بيغطي كل حاجة اتضافت أو اتغيرت في الـ API بعد الـ baseline المعروف بـ update-1. كل نقطة موثّقة بالتفصيل كمان جوه najeh_api_openapi.json (دوّر على كلمة update-2 في التاجز/الوصف/الملاحظات لأي إندبوينت لو عايز التفاصيل الخام: query params, request body schema, response example).

Backward-compatible كل التعديلات دي إضافية (additive) وليست breaking — أي تطبيق موبايل شغال حاليًا هيفضل شغال بدون أي تعديل، لأن أي حقل جديد له قيمة افتراضية (kind = "normal")، وأي endpoint جديد اختياري الاستخدام.

1) الفكرة الأساسية: فصل "الباقات" عن "الكورسات" (kind)

من أهم أجزاء هذا الـ update: كل صف في جدول courses بقى عنده عمود جديد اسمه kind، وقيمته واحدة من اتنين:

  • "normal" — كورس عادي زي ما هو دايمًا (وحدات، فيديوهات، امتحانات). ده الافتراضي، فأي كورس قديم في قاعدة البيانات اتحط له kind = normal تلقائيًا.
  • "package" — "باقة": نفس جدول الكورسات بالضبط (نفس الـ id، نفس كل الحقول)، لكن من غير محتوى تعليمي (مفيهاش وحدات/فيديوهات/امتحانات). الباقة بتتمحور حول:
    • جدول حصص أسبوعي (نفس نظام class_sessions المستخدم للكورسات العادية، فلترة بـ course_id — موثق تحت update-1).
    • ملفات (نفس فيتشر ملفات الكورس الموجود بالفعل).
مهم للموبايل
  • أي مكان بيرجّع كورس (list أو details) دلوقتي بيرجّع kind كمان. لو عايز تفرّق بين "كورساتي" و"باقاتي"، دلوقتي تقدر تفلتر أو تعرض badge مختلف بناءً على القيمة دي.
  • أي endpoint بيعرض قايمة كورسات (أدمن/معلم/طالب) بقى بيقبل query param اسمه kind (normal أو package) — لو مبعتوش، هترجعلك القائمتين مخلوطين مع بعض (كل صف عليه kind بتاعه).
  • لو kind == "package": متتوقعش تلاقي units/curriculum — دور بدل منها على جدول الحصص (/student/sessions/today?course_id=X&day=all) والملفات.

2) الطالب (Student)

2.1 GET /courses و GET /student/courses (نفس الـ handler بالظبط)

  • الجديد: query param اختياري kind (normal | package).
  • بدون توكن: الإندبوينت شغال حتى من غير تسجيل دخول (زي الأول تمامًا).
باج تم إصلاحه كان فيه نسخة تانية (قديمة/متروكة) من نفس الدالة اللي بترجّع الكورسات معرّفة في ملف تاني في الكود، وكانت هي اللي بتشتغل فعليًا بدل النسخة الصح (بسبب ترتيب الـ include) — يعني الفلتر بـ kind كان بيوصل للسيرفر بس مبيأثرش فعليًا. اتصلح، والسلوك دلوقتي مطابق تمامًا لما هو موثّق.

2.2 GET /courses/show و GET /student/courses/show (نفس الـ handler)

  • الجديد: حقل kind في رد تفاصيل الكورس.
  • إرشاد مهم للتكامل: لو kind == "package"، الـ curriculum/الوحدات هتيجي فاضية (ده طبيعي، مش error) — اجيب الجدول والملفات من الإندبوينتس المذكورة تحت.

2.3 GET /student/my-courses-progress

إندبوينت موجود من الأول بس مكنش موثّق خالص قبل كده — دلوقتي موثّق بالكامل.

إصلاح باج حقيقي كان بيحصل نفس مشكلة "نسخة مكررة من الدالة" المذكورة فوق، وكانت النتيجة إن حقلين كانوا بيختفوا من كل صف كورس بيرجع من الإندبوينت ده رغم إن الإصلاح كان موجود ومكتوب في مكان تاني من الكود:
  1. kind (كان دايمًا مفقود).
  2. teachers (array) — كان مفقود تمامًا.

دلوقتي: كل صف فيه kind + teachers[] (كل عنصر فيها {id, name, image, ...} — نفس الشكل المستخدم في تفاصيل الكورس في الأدمن/المعلم).

مثال رد:

{
  "status": "success",
  "data": [
    {
      "id": 229,
      "name": "باقة متابعة أسبوعية عامة",
      "kind": "package",
      "type": "recorded",
      "price": 49.99,
      "is_subscribed": true,
      "teachers": [
        { "id": 12, "name": "أ.محمد علي", "image": "https://.../teacher12.jpg" }
      ],
      "total_lessons_count": 0,
      "completed_lessons_count": 0,
      "progress_percentage": 0
    }
  ]
}

كمان بيدعم نفس kind query param فلتر لو عايز.

2.4 GET /student/sessions/today — معاينة جدول الباقة + قفل الانضمام أمنيًا

ده أهم تعديل من ناحية الأمان في كل الـ update.

المشكلة اللي كانت موجودة: طالب لسه مش مشترك في باقة معينة، مفيش وسيلة يشوف بيها جدول حصص الباقة قبل ما يقرر يشترك — الإندبوينت كان بيرفض أي طلب لكورس مش من ضمن كورسات الطالب المشترك فيها.

الحل:

  • لو بعتّ course_id في الـ query وكان الكورس ده kind = package، الإندبوينت دلوقتي بيسمح بمعاينة الجدول حتى لو الطالب مش مشترك فيه، عشان يقدر يشوف الأيام/الأوقات/المدرس قبل ما يقرر.
أمان لو الطلب اترجّع بسبب المعاينة دي بس (مش لأن الطالب فعلاً مشترك)، السيرفر بيمسح قيمة meeting_link ويرجّعها null في الرد. يعني الطالب يقدر يشوف إن فيه حصة يوم كذا الساعة كذا، بس مش هيقدر يفتح لينك الاجتماع أو ينضم للحصة اللايف غير لو مشترك فعلاً في الباقة. ده اكتشفناه واتصلح بعد ما لاحظنا إن أول نسخة من فيتشر "المعاينة" كانت هتسمح بالانضمام الفعلي لأي حد، مش بس المعاينة — اتقفل الفجوة دي فورًا.

للموبايل: لو بتعمل شاشة "تفاصيل الباقة" وفيها معاينة جدول قبل الاشتراك، ابعت course_id مع day=all، واتأكد إن زرار "انضم للحصة" بيكون مقفول/مخفي لو meeting_link جالك null (أو لو الطالب مش مشترك أصلًا).

2.5 POST /student/subscriptions/redeem-code

  • الجديد: لو كل الكورسات المرتبطة بالكود المُفعَّل من نوع kind = package، نوع الاشتراك الناتج (subscription_type) بقى "package" بدل "course" (كان دايمًا "course" قبل كده حتى لو الكود بتاع باقة).
ملاحظة تكامل لو الأدمن عمل كود تفعيل من غير ما يربطه بأي course_ids/subject_ids/teacher_ids خالص، التفعيل هيرجع success بس من غير أي صلاحية وصول فعلية. لو بتعمل شاشة أدمن لإنشاء أكواد في تطبيق الموبايل، تأكد إن فيه دايمًا حاجة واحدة على الأقل من التلاتة دول متبعتة.

3) الأدمن (Admin)

3.1 GET /admin/courses, GET /admin/courses/show, POST /admin/courses, PUT /admin/courses

مسارات موجودة من الأول، دلوقتي موثقة بالكامل لأول مرة.

  • الجديد الوحيد فعليًا: حقل/فلتر kind.
  • GET /admin/courses: query param kind (normal | package) — الفلاتر التانية كلها زي ما هي (subject_ids, teacher_ids, category_ids, academic_year_ids, price range, search, sort...).
  • POST /admin/courses: body field kind اختياري، افتراضي "normal" لو ما بعتّوش.
  • PUT /admin/courses: body field kind اختياري — لو اتبعت، بيغيّر نوع الكورس (ممكن تحول كورس عادي لباقة أو العكس). لو اتبعت قيمة غير normal/package، بيتجاهلها ويسيب الـ kind زي ما هو.
  • GET /admin/courses/show: حقل kind في رد تفاصيل الكورس.

مثال إنشاء باقة:

POST /admin/courses
{
  "name_ar": "باقة متابعة أسبوعية عامة",
  "price": 49.99,
  "kind": "package"
}

3.2 GET /admin/subscriptions و POST /admin/subscriptions

  • subscription_type بقى ليه قيمة جديدة ممكنة: "package" (بجانب course/subject/teacher/custom الموجودين من قبل).
  • القيمة دي بتتحدد من السيرفر تلقائيًا، مش حاجة الأدمن يبعتها — لو كل الكورسات المرتبطة بمنحة الاشتراك (grant) كلها kind = package، الرد هيرجع subscription_type: "package".
  • ده بيأثر على: GET /admin/subscriptions?subscription_type=package (فلترة جديدة) ورد POST /admin/subscriptions (نفس شكل الـ request القديم، بس الرد بيرجع النوع الصح).

3.3 GET /admin/notifications/inbox

إشعار "اشتراك جديد" (اللي بيوصل للأدمن لما طالب يشترك/يفعّل كود) بقى نصه يقول "باقة" بدل "كورس" لو الكورس المشترك فيه kind = package — بما فيها الصيغة النحوية الصح (مثلًا "باقتك" مش "كورسك"). مفيش تغيير في شكل الـ response نفسه، بس محتوى النص (title/body) اتغير.
نفس التغيير بالظبط بيوصل لإشعار المعلم (الـ push notification اللي بيوصله لما حد يشترك في كورس/باقة بتاعته).

3.4 GET /admin/exams

الكورس المُضمَّن جوه كل صف امتحان (لما يكون الامتحان مرتبط بكورس) بقى فيه kind كمان — تعديل بسيط، مفيش حاجة تانية اتغيرت.

3.5 POST /admin/consultations/recurring (إندبوينت جديد بالكامل)

شوف قسم "الاستشارات المتكررة" تحت — نفس تفاصيل نسخة المعلم بالظبط، بس بحقل إضافي teacher_id عشان الأدمن يقدر ينشئ نيابةً عن أي معلم.

4) المعلم (Teacher)

4.1 GET /teacher/courses, POST /teacher/courses, PUT /teacher/courses

  • نفس بالظبط منطق /admin/courses (فعليًا الـ backend بيستخدم نفس الدوال تحت الغطاء، مقيّدة على كورسات المعلم بس).
  • GET: فلتر kind زي الأدمن بالظبط.
  • POST: يتطلب subject_id (لازم يكون معيّن للمعلم ده)، وبقى فيه kind اختياري (افتراضي normal).
  • PUT: بيقدر يغيّر kind لكورساته بس (فيه تحقق ملكية قبل كده).

4.2 GET /teacher/sessions

الكورس المُضمَّن جوه كل حصة بقى فيه kind — يفيد المعلم يعرف من الليست نفسها إن الحصة دي حصة باقة ولا كورس عادي من غير ما يعمل call تاني.

4.3 POST /teacher/consultations/recurring (إندبوينت جديد بالكامل)

شوف القسم الجاي.

5) فيتشر جديد بالكامل: الاستشارات المتكررة (Recurring Consultation Slots)

المشكلة اللي بيحلها: قبل كده، المعلم كان لازم يضيف كل موعد استشارة لوحده يدويًا. دلوقتي يقدر يضيف موعد متكرر بيوم/أيام معينة في الأسبوع + وقت ثابت، لحد تاريخ معين، وهيتولد له موعد فعلي (row في consultation_slots) لكل تاريخ فعلي مطابق.

5.1 POST /teacher/consultations/recurring (المعلم)

الـ Auth: توكن المعلم نفسه (مفيش teacher_id في الـ body، بياخده من التوكن).

Request body:

{
  "days": ["Saturday", "Thursday"],
  "slot_time": "18:00",
  "end_date": "2026-10-15",
  "subject_id": 3,
  "meeting_type": "video_call",
  "type": "educational",
  "notes": "Weekly review session"
}
الحقلإلزامي؟ملاحظات
daysنعمarray من Saturday..Friday (أسماء إنجليزي، أول حرف كابيتال) — يوم واحد على الأقل
slot_timeنعمHH:MM، نفس الوقت لكل الأيام المختارة
end_dateنعمآخر تاريخ (شامل) يتولد لحده — أقصى حد 180 يوم من النهارده
subject_idلاسيبه فاضي لو الاستشارة نفسية مش تعليمية
meeting_typeنعمvideo_call / chat / online / offline
typeنعمeducational / psychological
notesلاملاحظات تظهر للطالب

السلوك بالتفصيل:

  1. لكل يوم في days: يبدأ من أقرب تاريخ مطابق لليوم ده (ممكن يكون النهارده نفسه لو مطابق)، وبعدين يزود 7 أيام في كل مرة لحد end_date (شامل).
  2. كل التواريخ الناتجة من كل الأيام بتتجمع مع بعض، وبتتشال أي تكرارات.
  3. حد أقصى للحماية: لو عدد التواريخ الناتجة أكتر من 200، الطلب بيترفض بالكامل (لازم تقسّم لأكتر من طلب).
  4. أي تاريخ فيه أصلًا موعد مطابق (نفس المعلم + نفس الوقت + نفس التاريخ) بيتم تخطيه مش بيتكرر ولا بيرجع error — الطلب بيكمل عادي والرد بيقولك كام اتعمل وكام اتخطى.
  5. إشعار واحد بس بيتبعت للمعلم عن كل العملية دي (مش إشعار لكل موعد لوحده).

Response:

{
  "status": "success",
  "message": "...",
  "data": {
    "created_count": 8,
    "skipped_count": 1,
    "slots": [ /* الصفوف الجديدة اللي اتعملت */ ]
  }
}

Errors محتملة (400): مفيش يوم متختار / الوقت أو end_date ناقصين / end_date في الماضي أو أبعد من 180 يوم / أكتر من 200 موعد هيتولدوا.

5.2 POST /admin/consultations/recurring (الأدمن)

نفس المنطق تمامًا حرفيًا (نفس دالة السيرفر تحت الغطاء، فمستحيل يحصل فرق سلوك بين النسختين مع الوقت). الفرق الوحيد: بيتطلب حقل إضافي teacher_id في الـ body (بما إن الأدمن بينشئ نيابةً عن معلم يختاره هو مش عن نفسه). لو الـ teacher_id مش موجود في قاعدة البيانات، بيرجع error.

{
  "teacher_id": 12,
  "days": ["Saturday", "Thursday"],
  "slot_time": "18:00",
  "end_date": "2026-10-15",
  "meeting_type": "video_call",
  "type": "educational"
}

5.3 من ناحية الطالب

مفيش أي تغيير مطلوب في تطبيق الطالب. أي موعد اتعمل (سواء من المعلم أو الأدمن) بيظهر تلقائيًا في نفس قائمة "المواعيد المتاحة" الموجودة بالفعل (GET /student/consultations/slots) ويتحجز بنفس الطريقة العادية.

ملاحظات ختامية للموبايل ديفيلوبر:
  • كل حاجة فوق متوافقة للخلف (backward-compatible) — مفيش endpoint اتشال، ومفيش حقل قديم اتغيّر شكله أو اتشال.
  • الحقل الوحيد اللي لازم تتأكد إنك بتتعامل معاه في كل مكان بيرجع كورس: kind (قيمته دايمًا normal أو package، وموجود دايمًا — مش nullable).
  • لو محتاج تفاصيل تقنية أدق (JSON schema كامل، أمثلة request/response كاملة لكل endpoint)، كل ده موجود جوه najeh_api_openapi.json تحت كل مسار مذكور فوق، ودور على أي وصف فيه كلمة update-2.
